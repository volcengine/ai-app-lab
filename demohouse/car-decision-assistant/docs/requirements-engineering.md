# 自然语言购车需求工程

这套链路的目标不是“从一段话里挑几个关键词”，而是把用户原话转成可追踪、
可核验、可继续编辑的原子需求，同时禁止模型凭记忆生成车型事实。

## 设计依据

- [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)：需求工程过程与需求信息项。
- [ISO 9241-210:2019](https://www.iso.org/standard/77520.html)：从用户、任务与使用环境出发的人本设计。
- [INCOSE Guide for Writing Requirements](https://www.incose.org/docs/default-source/working-groups/requirements-wg/gtwr/incose_rwg_gtwr_v4_040423_final_drafts.pdf)：一条需求只表达一个可验证意图，避免把多个条件合成一句无法判定的描述。
- [W3C PROV-O](https://www.w3.org/TR/prov-o/)：保存来源、派生过程和证据之间的追踪关系。
- [OMG SysML v2](https://www.omg.org/sysml/sysmlv2/)：需求、分析、验证与追踪的结构化关系。
- [Schema.org Automotive](https://schema.org/docs/automotive.html)：车辆、车型配置与常见汽车属性的通用语义参考。

这些标准没有规定购车产品的具体页面。本项目采用它们共同支持的原则：
保留原文、原子化、明确核验方式、把未知标为未知、记录证据来源。

## 正式处理链路

```text
用户原话
  → 原文分段与位置记录
  → 原子需求识别
  → 需求分类与核验计划
  → 精确车型事实查询
  → 条件 × 车型逐项评估
  → 待确认事项与证据回写
```

每个 `RequirementAtom` 至少包含：

| 字段 | 作用 |
| --- | --- |
| `sourceText`、`sourceStart`、`sourceEnd` | 回指用户原话，防止整理后无法解释 |
| `concept`、`title` | 稳定语义和用户可读名称 |
| `kind`、`scope` | 区分硬条件/偏好，以及场景/车型比较/交易条件 |
| `verificationMode` | 明确应由哪类证据核验 |
| `rule` | 仅在有明确数值或布尔条件时生成可执行规则 |
| `dataFieldHints` | 将需求路由到可能相关的专业数据字段 |

## 不丢失约束

1. 已识别的复合描述必须拆成单一意图，例如“外观/内饰好看”拆成外观审美和内饰审美。
2. 未命中已知语义的有效分句必须以 `unmapped_user_need` 保留，不能合并成“其他需求”。
3. 每项需求必须保留准确的原文位置；自动化测试会校验切片结果与 `sourceText` 完全一致。
4. 模型结果只用于补充结构，不覆盖确定性解析结果，也不能删除用户原话。
5. 一个车型事实只有在精确年款和配置身份一致时才能进入评估。
6. 没有足够证据时保持“待确认”，不得用模型常识补齐。

输入已包含年款和配置时，系统直接查询该完整名称并由返回身份再次校验；只有品牌、
车系或年款不足以唯一定位时，才展示专业数据返回的候选项。比用户输入更宽泛的
车系级或年款级结果不能被当成精确配置。

## 核验路由

| 需求类型 | 核验方式 | 示例 |
| --- | --- | --- |
| 精确配置与参数 | 专业数据集 | 能源类型、续航、辅助驾驶、影像、雷达、天窗、泊车、气囊、外观颜色 |
| 城市车系表现 | 汽车销量数据 | 指定城市、车系和月份范围的统计数据 |
| 时效性公开信息 | 当前不自动联网，保留为人工补充核验项 | 安全评价、车主口碑、保值信息 |
| 主观体验 | 本人试驾或实车确认 | 后排舒适、空间感受、外观内饰、驾驶平稳 |
| 交易条件 | 正式报价或订单确认 | 落地总价、费用构成、赠品 |
| 使用背景 | 记录为场景，不参与车型事实判定 | 通勤距离、乘员、公司充电条件 |

“尺寸大”不自动等于“乘坐舒适”，“销量高”也不自动等于“适合该用户”。
专业数据只能回答其统计口径或配置字段覆盖的问题。

## 汽车专业数据核验

开发时必须用“精确车型 + 完整配置详情”验证真实返回结构，并在项目记录中保存
本次查询的来源时间与 trace/request ID。公开仓库不保存具体调用标识或 Provider
原始响应；字段覆盖、版本和统计口径始终以用户当前账号的实际返回为准。

外部调用设置了分阶段时限：完整配置 15 秒、聚焦配置 20 秒、车型身份 50 秒、
城市数据 20 秒。车型身份查询需要返回完整候选列表，因此允许更长时间；其余调用
超时不会变成虚假答案，而是保存已识别需求，并把没有可靠返回的相关事实标为
“待确认”。

## 扩展新需求

在 `lib/requirements.ts` 的定义表中新增稳定语义、触发表达和核验方式；涉及专业
数据时，再为 `dataFieldHints` 增加解析映射。随后至少添加三类测试：

1. 标准表达；
2. 口语、倒装或不完整表达；
3. 未知表达仍被原样保留。

不得只给提示词增加一条示例而不增加确定性回退与测试。
